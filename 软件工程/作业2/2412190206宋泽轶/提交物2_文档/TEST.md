# 测试文档：Homework2 Workflow MVP 可行性测试

本文档教你怎么**主动验证**这个 3-Agent 协作 Workflow 是否可行。
项目根目录：`Homework2-Workflow-MVP/`

---

## 一、测试目标（对应 PPT 评审要点）

| 验证点 | 对应 PPT 要求 | 怎么算「可行」 |
|--------|---------------|----------------|
| 流程完整性 | 端到端跑通 | 3 个 Agent 依次执行、三个产出文件都生成 |
| Agent 协作/互通 | 消息传递 + 状态共享 | 下游 Agent 产出的内容里包含上游需求/设计产物 |
| 可运行性 | MVP 可运行即可 | 不装任何 Key、不联网也能跑通（mock 模式） |
| 鲁棒性 | —— | 空需求、英文、特殊字符都不报错 |

---

## 二、三种测试方法（任选，推荐先用 A）

### 方法 A：自动化测试（最省事，一键验证）[推荐]

```bash
cd Homework2-Workflow-MVP
python test_workflow.py
```

脚本会跑 12 个检查项，全部打印 `[PASS]` 且最后显示
`总计: 12/12 通过` 和 `结论: 项目可行性验证通过 (可行)`，即可判定可行。
（若某项为 `[FAIL]`，脚本会给出原因，按提示修改即可。）

覆盖用例：
1. 共享状态写入/读取、下游读取上游产物、通信日志完整
2. 需求/设计/编码三个 Agent 产出质量 + 信息互通
3. 端到端跑通 5 段产品需求描述：中文、中文业务、英文、空、特殊字符

### 方法 B：手动功能测试（用测试数据，直观看产出）

测试数据见同目录 `sample_requirements.txt`（直接复制粘贴，也可抄下表）。
手动运行时你**自己输入一段产品需求描述**，需求 Agent 会把它标准化成需求文档。

| 编号 | 输入（产品需求描述） | 类型 | 预期产出 |
|------|----------------------|------|----------|
| T1 | `我想做一个帮助团队管理任务的待办事项系统，支持创建任务、设置截止日期、标记完成，并支持多人协作。` | 中文默认 | output/ 下 3 个文件均非空 |
| T2 | `用户想要一个在线订餐平台，支持浏览菜单、下单、查看订单。` | 中文业务 | 设计/编码产出包含「标准化软件需求文档/技术设计文档」字样（互通证据） |
| T3 | `Build a student grade management system with course and score tracking.` | 英文 | 三个文件均正常生成，无乱码 |
| T4 | （直接回车，不输入） | 空需求 | 自动使用默认需求示例，不报错 |
| T5 | `Test #1 & 'quote' project description.` | 特殊字符 | 流程不崩溃，正常产出 |

**操作步骤：**
```bash
python main.py
```
根据提示依次输入 T1~T5 的需求描述，每次回车后观察：
- 终端是否打印 `Workflow 完成：3 个 Agent 已通过共享状态完成信息互通。`
- `output/` 目录下 `requirement.md`、`design.md`、`code.py` 是否更新且内容合理

**判定可行：** 每次都打印完成提示，且 `output/` 三个文件非空、内容与该需求描述相关。

### 方法 C：真实免费引擎测试（进阶，验证「真 Agent」）

`llm.py` 内置 3 个免费引擎，在 `main.py` 取消注释对应行并配置 Key 后即可启用：
- Ollama（本地）：`ollama pull qwen2.5:7b`
- Gemini：`set GEMINI_API_KEY=你的key`
- Groq：`set GROQ_API_KEY=你的key`

启用后重复方法 B，观察产出是否变为真实模型生成的内容（不再是模板）。

## 三、如何判断「可行性」成立（验收清单）

- [ ] 方法 A 脚本输出 `12/12 通过`
- [ ] 方法 B 中 T1~T5 都能跑完且 `output/` 三文件生成
- [ ] T2 的 `design.md` / `code.py` 中能看到「标准化软件需求文档」「技术设计文档」字样（证明上游→下游信息互通）
- [ ] 空需求（T4）不报错

满足以上即证明：该项目满足 PPT「至少 2 个 Agent 协作、Agent 间通信、顺序流程控制、可运行」的全部硬性要求，可行性成立。

---

## 四、常见问题排查

| 现象 | 原因 | 解决 |
|------|------|------|
| 终端输入中文后文件乱码 | 个别旧终端 stdin 编码问题 | 用回车默认需求或英文需求；文件本身以 UTF-8 保存 |
| 启用真实引擎报错 | 未启动 Ollama / 未设 Key / 断网 | 检查本地服务与 `GEMINI_API_KEY`/`GROQ_API_KEY` 环境变量 |
| `No module named ...` | 依赖未装 | `pip install -r requirements.txt` |

## 五、本次实测记录（学生成绩管理系统）

按「方法 B」手动运行 `python main.py`，输入：
```
帮我写一个学生成绩管理系统，能录入学生成绩、自动计算每门课的平均分，并按总分从高到低排名。
```

**终端关键过程：**
```
[通信] User -> 状态 'user_requirement' (写入 45 字符)
>>> 步骤：运行 需求Agent
    [通信] 需求Agent -> 状态 'requirement' (写入 221 字符)
>>> 步骤：运行 设计Agent
    [通信] 设计Agent -> 状态 'design' (写入 308 字符)
>>> 步骤：运行 编码Agent
    [通信] 编码Agent -> 状态 'code' (写入 1075 字符)
Workflow 完成：3 个 Agent 已通过共享状态完成信息互通。
```

**Agent 间信息互通的实锤证据：**
- `design.md` 的「依据需求（节选）」包含**需求文档原文** → 证明设计 Agent 读取了需求 Agent 产物
- `code.py` 的「依据设计 Agent 产出（节选）」包含**设计文档内容** → 证明编码 Agent 读取了设计 Agent 产物

**判定：** 满足验收清单全部项（三产出齐全、互通证据可见、空需求不报错），可行性成立。
